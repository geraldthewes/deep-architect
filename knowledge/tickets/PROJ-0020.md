# Review driver

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan
> **Origin**: Operator need for one command that runs the review pipeline; absorbs PROJ-0019 (novelty-based outer loop)
> **Strongly benefits from**: PROJ-0018 (novelty metrics / compare report)

## Problem Statement & Business Context

**What problem are we solving?**
The review pipeline is a manual, easy-to-get-wrong shell ritual. There is no single driver that runs the tools in order or decides whether to go again. Artifacts land wherever the operator happened to redirect them — no standard place in the repo.

Primary use case is **PR review** (source branch vs target branch), not an arbitrary git range:

```bash
ocr review --from main --to BRANCH ... > code-review-rN.json
review-analyzer --output-dir feedback-rN ... code-review-rN.json
review-action feedback-rN/
# human judges whether to run again
```

Raw OCR count is a bad stop signal. On plant-tracking PROJ-0013, findings went 29 → 31 → 36 while high severity edged down and low severity rose. A driver must stop on **novelty of high-signal findings**, not “OCR is empty.”

**Why is this important?**
- One command for local interactive use and later CI, aimed at reviewing a PR branch against `main` (or another target)
- Multi-pass review is slow and easy to mis-judge (“still N findings” ≠ “not done”)
- A standard, configurable output directory makes artifacts findable, resumable, and CI-cacheable
- Once catalog memory (PROJ-0016) and action gates (PROJ-0017) exist, the loop can actually terminate

**Who needs this?**
Gerald and anyone dogfooding the OCR → analyzer → action pipeline locally; the same driver should be runnable unattended in CI.

## Requirements & Scope

### Must-Have Features
- One orchestrator CLI (name TBD in planning, e.g. `review-driver`)
- **PR-first inputs**: `--source` (PR branch) and `--target` (base branch, **default `main`**). Working repo root, max passes, optional K for consecutive zero-novelty
- **Standard review output directory** in the application repo:
  - Documented default path (exact path chosen in planning)
  - Override via CLI flag and/or config
  - All per-pass artifacts live under it (`…-r{N}.json`, `feedback-rN/`, run state, final report)
- Per pass: run `ocr review` (source vs target) → `review-analyzer` → `review-action` → compute novelty → continue or stop
- Stop when novelty of high/medium VALID findings (post-dedup, post-catalog) is 0 for K consecutive passes (default K=2, configurable)
- Safety: `--max-passes` (required or default low, e.g. 5); optional stop on action-error threshold
- Must **not** stop only because total OCR comments is small if high VALID novelty remains; must **not** require total OCR comments == 0
- Persist a run state file (pass index, novelty history, artifact paths) so a run can resume
- Human-visible per-pass summary + aggregate report at end
- CI-friendly exit codes: 0 if converged; non-zero if errors or max-passes with remaining novelty
- Tests, README, quality bar (`ruff` / `mypy` / `pytest` / `bandit`)

### Nice-to-Have Features
- Dry-run (OCR + analyzer, no action)
- Cost / pass budgets
- Notify on converge
- Config file for default excludes, models, concurrency
- Machine-readable JSON summary for CI

### Out of Scope
- Implementing catalog memory (PROJ-0016) or action gates (PROJ-0017) — hard dependencies
- Replacing OCR with a custom reviewer
- Architecture adversarial-sprint harness changes
- Auto-merge / auto-PR to main
- review-browse TUI (PROJ-0015)

## Constraints & Context

**Integration Points**: External `ocr` CLI (PR diff: target…source); internal `review-analyzer`, `review-action`; optional `review-compare` (PROJ-0018). Git repo must be usable by review-action (existing commit assumptions). Output directory lives in the application repo under review.

**Preferred Technologies**: Same packaging as other deep-architect CLIs. Plain async/CLI orchestration. No LangGraph / LangChain / new agent framework.

**Constraints**:
- Safe-by-default: low max-passes, gates on, write-backlog on
- Do not swallow exceptions; log and propagate; surface pass-level failures
- Run from the application repo root
- Prefer not to implement until PROJ-0016 and PROJ-0017 are dogfooded on a real branch
- Do not require plant-tracking as a test dependency; use fixtures

## Success Criteria

### Automated Verification
- [ ] Stop logic unit tests: novelty sequences `[3,1,0,0]` stop at pass 4 for K=2; `[1,1,1]` hits max-passes
- [ ] Orchestrator wires steps in order with injectable runners (no live OCR/LLM)
- [ ] State file records pass artifacts and novelty history; resume continues from last pass
- [ ] Default output directory is used when no override is given; override flag/config is honored
- [ ] CLI requires a source branch; target defaults to `main` when omitted
- [ ] README documents usage, output layout, source/target semantics, prerequisites (0016/0017), flags, failure modes, human vs CI
- [ ] `ruff`, `mypy`, `pytest`, `bandit` pass

### Manual Verification
- [ ] After 0016+0017 on plant-tracking (or similar): run `--source <pr-branch>` with max-passes=3–5; observe declining novelty; either converge or stop at max with a clear report under the standard output dir
- [ ] Without 0016 memory, the driver does **not** silently claim convergence while re-fixing backlog themes
- [ ] Same command is usable locally and as a CI step (exit code + artifacts)

**End State**: `review-driver --source <pr-branch>` (target `main` unless overridden) runs multi-pass PR review, writes all artifacts under a standard configurable repo directory, and stops when high-signal novelty is gone for K passes (or max reached) — locally and in CI.
