# review-analyzer: catalog-aware triage, prior feedback, and intra-OCR dedup

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan  
> **Origin**: Analysis of 3 review passes on plant-tracking PROJ-0013 (P0 improvements)

## Problem Statement & Business Context

**What problem are we solving?**
`review-analyzer` triages each OCR finding in isolation. It does **not** consult `knowledge/backlog/`, `knowledge/tickets/`, or prior feedback directories when choosing `VALID` / `REJECTED` / `BACKLOG`. Across three plant-tracking PROJ-0013 passes, the same **themes** (type hints on public APIs, Form/Body shape for `mark_plant_dead`, test docstrings, generated client URL nits) reappeared every pass with different wording. Exact-text match across passes is near zero; semantic recurrence is high.

Post-hoc backlog promotion (`backlog_dedup.py` / `backlog_store.py`, commit `1a58db8`) only runs **after** verdicts are chosen and only for findings already marked `BACKLOG`. It records deferred work for humans; it does **not** prevent the next pass from reclassifying the same theme as `VALID` (and thus auto-fixed by `review-action`).

Additionally, a single OCR run can emit near-duplicate comments on the same file (e.g. two conftest findings about one-time iterators), doubling analyzer cost and action work.

**Why is this important?**
Without classification-time memory:
- Manual multi-pass review loops cannot converge on “nothing new”
- Already-deferred work is re-litigated every pass
- Auto-fix may thrash on backlog-territory themes (type-hint campaigns, style)
- Plant-tracking evidence: 29 → 31 → 36 findings while core death-field quality improved but theme noise did not drop

**Who needs this?**
Anyone running `ocr review` → `review-analyzer` → `review-action` repeatedly on a long-lived branch (e.g. feature branches under active review).

## Requirements & Scope

### Must-Have Features (MVP)

1. **Classification-time knowledge catalog**
   - Load compact catalog from `--knowledge-dir` (default `<cwd>/knowledge`): backlog + ticket titles/paths (reuse `load_full_catalog`)
   - Inject catalog into the triage prompt for each finding (or equivalent batch design if planning finds a cheaper correct approach)
   - Instruct the LLM: if the finding is the same *core issue* as an existing backlog or ticket entry → do **not** mark `VALID` for auto-fix; mark deferred (`BACKLOG` or new verdict — see open questions) and record `match_path` when known
   - When catalog is empty/missing, behavior matches today (no hard failure)

2. **Prior feedback memory**
   - CLI: `--prior-feedback <dir>` (repeatable) or comma-separated list
   - Build a compact “already triaged” index from prior report markdown (file path + short comment/preview + verdict + optional disposition)
   - Same-theme findings should prefer `BACKLOG` / `REJECTED` / already-deferred over `VALID` when prior pass already deferred or rejected them
   - Document that prior dirs are read-only inputs (no mutation of old feedback files required for MVP)

3. **Intra-OCR near-duplicate collapse**
   - Before (or as part of) triage: group comments by path + similarity of content
   - Keep the highest-severity (or first) as canonical; mark others as duplicates of the canonical id
   - Duplicates must not consume full LLM triage by default (cheap rule or single batch decision); they appear in INDEX/SUMMARY with a clear `DUPLICATE` (or equivalent) disposition
   - Unit-testable pure function for grouping

4. **TIMEOUT / infra hygiene**
   - Confirm `TIMEOUT` is never promoted as intentional backlog without re-triage
   - Legacy timed-out `BACKLOG` text in old reports is not treated as real backlog themes when building prior-feedback index (filter or flag)
   - SUMMARY clearly separates timeout/infra counts from true backlog

5. **Backlog promotion remains on by default** after triage (existing behavior); catalog-aware triage should *feed* better backlog content, not replace promotion

6. **Tests, docs, quality bar**
   - Unit tests for catalog injection plumbing, prior-feedback index loading, duplicate grouping, and “empty catalog” fallback
   - No live LLM calls in unit tests (project convention)
   - README section: how multi-pass memory works; example with plant-tracking feedback dirs
   - `ruff` / `mypy` / `pytest` / `bandit` clean

### Nice-to-Have Features (post-MVP)

- New explicit verdict `KNOWN` / `ALREADY_BACKLOG` for clearer convergence metrics (vs overloading `BACKLOG`)
- One-shot CLI to backfill `knowledge/backlog/` from existing feedback dirs (plant-tracking P1–P3)
- Embedding-based similarity instead of string/heuristic similarity for duplicates and prior match
- Batch “pre-filter” LLM call that maps all findings to catalog in one shot (cost optimization)

## Success Criteria

### Automated Verification
- [ ] With a fixture catalog containing a known theme, a finding about that theme is **not** classified VALID when the mock/stub triage path exercises catalog rules (unit-level contract tests for prompt contents + post-parse match stamping)
- [ ] `--prior-feedback` loads prior reports and includes them in the analysis path (assert prompt or prefilter input)
- [ ] Duplicate grouping collapses near-identical same-file comments; only one canonical requires full analysis in the pipeline design
- [ ] TIMEOUT findings are excluded from backlog promotion
- [ ] Empty knowledge dir / no prior feedback: behavior unchanged from current defaults
- [ ] README documents new flags and multi-pass usage
- [ ] `ruff`, `mypy`, `pytest`, `bandit` pass

### Manual Verification
- [ ] On plant-tracking: seed or promote backlog from a pass, re-run analyzer on a later OCR JSON with `--prior-feedback` pointing at earlier dirs; recurring type-hint / Form-Body themes are deferred rather than VALID
- [ ] SUMMARY shows timeout vs true backlog distinctly
- [ ] `knowledge/backlog/` under plant-tracking receives creates/updates when BACKLOG verdicts remain

**End State:** Multi-pass `review-analyzer` runs use durable knowledge + prior feedback so already-deferred themes are not re-opened as VALID, and near-duplicate OCR noise is collapsed within a single pass.

## Research Questions for Planning Phase

- Prefer overloading `BACKLOG` vs new `KNOWN` / `DUPLICATE` verdicts?
- Catalog in every per-finding prompt vs one pre-pass matcher LLM call (cost vs accuracy)?
- Similarity algorithm for intra-OCR dedup (token overlap, normalized Jaccard, optional embedding)?
- Should prior-feedback matching be pure heuristic first (file + keyword) with LLM only on ambiguous cases?
- How to stamp `match_path` on feedback markdown consistently with existing disposition stamps from promotion?
